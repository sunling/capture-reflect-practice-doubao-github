# Develop Practice｜把记录发展成实践

## GitHub 仓库配置（安装前必填）

目标记录仓库：`YOUR_GITHUB_USERNAME/YOUR_REPOSITORY`

安装本 Skill 前，必须把上面的占位符替换为实际的 `owner/repository`。所有读取、搜索、创建和更新只在这个仓库中进行；若占位符尚未替换、仓库不存在或当前 GitHub 工具无权访问，停止执行并请用户提供或确认仓库，不搜索、猜测或改写其他仓库，也不退回临时本地文件冒充保存成功。分支未另外指定时使用该仓库的默认分支。

## 目标

把已经在生活里发生的事情整理成可以持续行动、观察和接收反馈的实践，而不是从一个孤立念头制造项目。

实践的最小闭环是：

```text
`journals/` / `notes/` 中出现线索
→ 确认重复、行动或反馈证据
→ 定义一个最小实践
→ 做一轮真实行动
→ 记录反馈
→ 决定继续、调整、暂停或结束
```

## 边界

- 只有一个刚出现的念头，没有行动或反馈：先留在 `journals/` 或 `notes/`；
- 只是要保存一条经历或输入：分别使用 `capture-journal` 或 `capture-note`；
- 只是想回看最近记录：先使用 `weekly-review`；
- 已经有输出练习，只是围绕选定主题追问、写作或继续修改草稿：使用 `new-article`；
- 一次性待办：直接行动，不必建立实践。

## 开始前读取

- 根目录 `README.md` 与 `PROFILE.md`（如存在）；
- 支持这项实践的少量 `journals/` 和 `notes/`；
- `practices/README.md`（如存在）；
- 若 `practices/` 中已存在同名或近义实践，读取其 `mission.md`、`current.md` 和本轮必要材料。

不要为了显得完整扫描全部历史。若证据不足，明确说明缺少什么，并建议继续观察。

## 证据门槛

在 `practices/` 中创建新实践前，至少确认以下一项：

1. **重复**：同一需要、问题或主题在多条记录中出现；
2. **行动**：用户已经做过至少一次真实尝试；
3. **反馈**：已经得到自身感受、行为变化、他人回应或环境结果。

把证据写成日期与相对路径。不要把计划写成已经发生，也不要从短期情绪推断长期人格。

## 新建实践

### 1. 先确认边界

和用户确认：

- 实践名称；
- 它为什么存在；
- 首先服务谁；
- 当前做什么；
- 本轮明确不做什么；
- 如何观察反馈；
- 什么时候回看。

名称应具体、可辨认，使用仓库相对目录：

```text
practices/<实践名>/
```

不要创建“思考”“成长”“知识沉淀”等只有分类意义的空泛实践。

### 2. 创建最小结构

```text
practices/<实践名>/
├── mission.md
├── current.md
└── drafts/      # 只有输出练习开始产生文章时才增加
```

`mission.md` 建议结构：

```markdown
# 实践名称

## 为什么存在

## 服务谁

## 做什么

## 不做什么

## 来源

- 相关日记记录 / 笔记：仓库相对路径
```

`current.md` 建议结构：

```markdown
# 当前一轮

## 当前假设

## 本轮行动

## 如何观察反馈

## 下次回看

## 本轮不做
```

只保留有真实材料的部分，不用空话填满模板。

如果这是会持续产生文章的输出练习，仍先建立 `mission.md` 和 `current.md`；第一篇文章开始起草时，再由 `new-article` 增加 `drafts/` 并管理其中草稿。单篇文章主题不能替代实践名称。

### 3. 保留来源关系

- 使用相对链接连接 `journals/` 或 `notes/` 中支持它的记录；
- 原始记录保留时间现场，不因为进入 `practices/` 而删除或搬走；
- 不复制同一份正文到多个目录；
- 需要引用时，只带入与当前行动直接相关的部分。

## 更新现有实践

若目录已存在：

1. 优先更新 `current.md`，不要创建近义实践；
2. 使命、对象或长期边界没有改变时，不重写 `mission.md`；
3. 先区分事实、用户判断和 AI 建议；
4. 记录本轮已经发生的行动与反馈，再决定下一轮；
5. 下一轮只保留一个足够小、能够真实完成的行动；
6. 允许暂停或结束。停止不等于失败。

若需要保留多轮历史，先遵循该实践已有约定；没有约定时，不自行搭建复杂归档层级，先询问用户。

## 反馈与回看

反馈可以是：

- 身体或情绪感受；
- 行为变化；
- 他人回应；
- 作品、服务或环境中的可观察结果；
- 原假设被推翻或变得更具体。

不强迫量化，也不把赞美当作唯一正反馈。回看时至少回答：

- 实际做了什么？
- 发生了什么反馈？
- 哪个假设得到支持、被挑战或仍不确定？
- 下一轮是继续、调整、暂停还是结束？

## 隐私与事实边界

- 只读取和写入当前 `practices/` 子目录必要的材料；
- 涉及第三方、身体、医疗、关系或工作信息时，遵循 `PROFILE.md` 的隐私边界；
- 不编造用户的使命、受众、行动、反馈或承诺；
- 准备公开内容前，单独标记需要匿名化、授权或删除的细节。

## GitHub 执行方式

1. 使用豆包中已授权的 GitHub 工具。没有明确的记录仓库时先询问，不猜测用户名、仓库名或分支。
2. 从仓库默认分支读取相关 `journals/`、`notes/` 以及已有的近义实践。`practices/` 尚不存在时，可随第一份 `mission.md` 一起创建；GitHub 不需要预先创建空目录。
3. 新建实践时在同一次变更中写入 `mission.md` 与 `current.md`；更新时先完整读取最新文件，只改动本轮确实变化的部分。
4. 提交信息应简短明确，例如 `Start <practice-name> practice` 或 `Update <practice-name> practice`。
5. 更新前使用 GitHub 返回的最新文件版本信息；遇到冲突或文件已变化时重新读取，不强制覆盖。
6. 只有 GitHub 返回创建、更新或 commit 成功，才可以说已经保存。成功后简短报告相对路径、变更内容，以及 GitHub 文件链接或 commit 结果。

当前环境没有 GitHub 写入能力时，不要声称已经保存；输出建议路径、`mission.md` 与 `current.md` 的完整内容，以及仍需要用户确认的边界或事实。

## 完成检查

- 是否有重复、行动或反馈中的至少一类证据？
- 是否链接了 `journals/` 或 `notes/` 中的具体记录，而不是只写抽象理由？
- 是否只定义了一个足够小的本轮行动？
- 是否写清本轮不做什么和下次回看时间？
- 是否避免创建近义实践或复杂中间层？
- 是否把解释权和继续与否的决定留给用户？
